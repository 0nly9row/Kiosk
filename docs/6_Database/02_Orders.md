# 2. 주문 (Orders)
- 현재 상태: Orders 생성과 제약조건 검증 완료.
- 주문 한 건에 대한 공통 정보를 저장한다.
- 확정: OrderId(주문번호), OrderTime(주문시간), OrderStatus(주문상태)
- 제외: TotalCount(총수량), TotalPrice(총합계)

## <전체 테이블 초안>
열 이름	        자료형	          역할
OrderId         int               내부 식별값
OrderTime       datetime2(0)      주문 행 INSERT 시점 시각
OrderStatus     nvarchar(20)      주문 상태 저장


## <연동 예정 흐름>
C# 주문 버튼 클릭
├─ 1. 트랜잭션 시작
├─ 2. Orders INSERT 및 ID 반환
├─ 3. OrderDetail INSERT 
└─ 4. 전체 저장 성공?
      ├─ 1. [성공] COMMIT, ReceiptData 구성 후 영수증 표시
      └─ 2. [실패] ROLLBACK, 실패 안내 및 장바구니 유지

[주요 부분]
- Orders INSERT는 주문 행 생성 시점이다.
- COMMIT은 주문 전체 저장 성공 시점이다.
- 두 시점은 같다는 보장이 없다.

## <구조 대응>
C#_ReceiptData	 DB_Orders
화면 표시용 모델	 영구 저장 테이블
OrderNumber	 OrderId (ReceiptData.OrderNumber로 전달)
OrderTime	         OrderTime (ReceiptData.OrderTime로 전달)
TotalCount	         OrderDetail의 수량 합계 계산 (ReceiptData로 전달)
TotalPrice	         OrderDetail의 가격 합계 계산 (ReceiptData로 전달)
Items	                 OrderDetail의 조회 결과로 구성 (ReceiptData로 전달)
                         OrderStatus (DB의 주문 상태, 별도 저장)

## <Orders 테이블을 구성한 후 후속 구현 후보>
1. 주문 저장 실패 처리 및 로그
- INSERT 실패나 트랜잭션 롤백 시 번호에 공백이 생길 수 있음
 → ex. 1 > 2 > 4 > 5 
- OrderId의 공백은 반드시 오류를 의미하지 않는다.
- 실제 주문 저장 실패는 오류 원인을 확인할 필요가 있음
 → 따라서 실패 로그를 남기는 방식을 구현할 예정
 → 로그 저장 방식은 미정. 
 → 이는 향후 주문 저장 실패 및 트랜잭션 테스트에도 연결 가능
- 이때 저장 성공 기준은 아래와 같다.
 → 주문 헤더와 상세를 같은 트랜잭션에 저장하고, 
   커밋 성공 후 영수증을 표시한다
 → 헤더를 INSERT해서 OrderId를 받았어도 
   상세 저장에서 실패하면 주문 전체가 롤백될 수 있다

2. 주문 취소 구현
- C# 키오스크에서 주문 조회 화면을 만들고, 
 그 화면애서 저장된 주문을 선택하고, OrderId로 취소를 요청
- DB에서는 해당 주문의 접수 상태를 취소로 변경
 → 취소된 내역을 삭제가 아닌 상태 표시로 해뒀기 때문에
    이후 취소된 내역도 조회 가능

ex. 
UPDATE dbo.Orders
SET OrderStatus = N'취소'
WHERE OrderId = @OrderId
  AND OrderStatus = N'접수';

## <1. 주문 식별값(OrderId) 열 설계>
1. OrderId 하나만 사용하여 설계
- DB 자동 증가 정수를 주문번호로 사용.
- Orders를 INSERT한 직후 OrderId 및 OrderTime을 받음.
 → 같은 트랜잭션 안에서 그 값을 OrderDetail.OrderId에 넣어야 하기 때문
 → ReceiptData에 반영 및 영수증 표시 시점은 커밋 성공 후로 잡음

2. 장점
- 테이블과 C# 연동이 간단함.
- 주문번호를 별도로 생성할 필요없다.
- 기존 C#_ReceiptData와 연계 가능.

3. 단점
- 내부 식별값이 영수증에 그대로 노출됨.
- 번호가 빈틈없이 연속되지는 않음.

4. 자료형 결정 이유
- 'int'
→ 현재 주문 규모에는 int의 범위가 충분하다.


5. 역할
① DB에서의 역할
- 기본키(PK)로 식별자
- 주문 한건을 유일하게 구별하는 기준
- OrderDetail에서 참조할 예정
→ 예시 (관계 설명용, 미구현)
Orders
└─ OrderId = 1

OrderDetail
├─ OrderId = 1, 상품 A
└─ OrderId = 1, 상품 B

② C#_Kiosk
- 주문 저장 후 생성된 OrderId를 전달받는다.
- OrderId를 문자열로 변환함.
- ReceiptData.OrderNumber에 전달함.
- ReceiptForm에서 주문번호로 표시함.
- 저장 성공이 확인된 후 전달하는 방향.
- 실제 반환/전달 로직은 미구현.


6. 제약 조건 구상
① PRIMARY KEY
- 각 행을 유일하게 식별한다
- null을 허용하지 않으며 한번 부여되면 
 중복된 값을 다른 행에서 사용할 수 없는 것

② IDENTITY
- 새로운 번호를 자동 부여하는 것
 → IDENTITY(시작 번호, 증가 간격)
- 새 주문을 INSERT할 때 1부터 시작하여 증가하도록 번호를 생성.
 → IDENTITY(1,1)

7. 주의점
- Orders 테이블은 C#_ReceiptData와 관계가 있지만 
 역할이 다르며, 두 구조의 속성이 동일할 필요는 없다
- ReceiptData의 StoreName과 StoreDescription은 
 매장 표시용 정보로 DB에 저장할 이유 없다.

- OrderId가 주문 번호 역할을 하게 되면
 주문 번호 전용 열이 없기 때문에 아래와 같은 요구가 있다면 
 '별도의 번호 전용 열(ex. OrderNumber)'이 더 유용할 수도 있음
 → 매일 주문번호를 1번부터 시작.
 → 매장마다 다른 번호를 사용.
 → 주문 식별번호와 호출번호를 구분.
- 그러나 지금은 주문 저장 및 조회가 주요 목적임.
 따라서 주문번호 전용 열이 굳이 필요없음
- 만약 INSERT 실패나 트랜잭션 롤백 시에도 번호가 소모가 될 수 있음.
 → 번호의 공백이 생길 수 있는데 이것만으로 저장 실패를 단정 못 함.
 → 저장 실패에 대한 로그는 나중에 자세히 해본다. 
   (<Orders 테이블을 구성한 후 후속 구현 후보>)

## <2. 주문 시간(OrderTime) 열 설계>
1. 설계 대안
- 현재는 C#에서 DateTime.Now를 이용해 생성했었음.
 → C#에서 시간을 한 번 만드는 방식을 고수하면
   이 값을 DB와 영수증에 쓰는 방식으로 대안을 만들 수 있음.

- 하지만 SQL Server에서 주문시간 생성하는 방식으로 결정.
 → 주문 행이 INSERT될 때, 
   DB가 주문 저장 시각을 정하고,
   C#에서 전달받아 영수증에 표시하는 방식으로 결정
 → DB가 Orders에 주문 행을 insert 시점을 기록하는 점이 핵심.
    (주문 전체가 커밋된 시각과 결제 승인 시각과 별개.)


2. 장점
- Orders에 주문 행을 INSERT하는 시점으로 정했으므로, 
 C#이 해당 값을 생략해도 DB가 주문 시각의 기준이 된다.


3. 단점
- 영수증에 저장된 시각을 표시하려면 
 INSERT에서 생성된 OrderTime을 C#으로 돌려받아야 한다.
- OrderId와 함께 반환받을 수 있다.


4. 자료형 결정 이유
'datetime2'
- 날짜와 시간을 함께 저장할 수 있음.
- 기존 C# DateTime과 연결 가능함.
- 초 이하 정밀도를 지정할 수 있음.
- 정밀도는 아래의 목적을 가지기 때문에 (0)으로 결정
 → 주문이 언제 발생했는지
 → 영수증에 주문 시간을 표시하고
 → 날짜별 주문 내역 조회


5. 역할
① DB에서의 역할
- 주문 한 건이 저장되는 시각을 기록
 → Orders 행이 INSERT될 때 기록하는 시각
- 주문 내역 조회 시 시간 정보 제공.

② C#_Kiosk
- 커밋 후 DB의 OrderTime을ReceiptData.OrderTime에 반영.
- ReceiptForm은 전달된 시각을 표시.
- 실제 DB 연동 코드는 아직 미구현.


6. 제약 조건 구상
① NOT NULL
- 주문시간이 NULL로 저장되지 않게 함.

② DEFAULT
- INSERT에서 DB 현재 시각을 넣도록 한다
- 서버 현지 시각으로 사용한다.
 → 'SYSDATETIME()'
- 주의. 
 → DEFAULT는 명시적으로 입력한 NULL은 자동으로 대체가 안된다.


7. 주의점
① datetime2의 정밀도란?
- 날짜와 시간에서 '초 아래의 값'을 몇 자리까지 저장할지 결정하는 것.
→ 시:분:초:밀리초
→ 1초는 1000밀리초
ex. datetime2(0): 14:30:25
ex. datetime2(3): 14:30:25.123

## <3. 주문 상태 (OrderStatus) 열 설계>
1. 설계 대안
- Orders에 OrderStatus 열을 둔다.
- 상태를 문자열로 '접수', '취소'처럼 저장한다.
 → 숫자로 1은 접수, 2는 취소처럼 저장할 수 있다
    이 방식은 C#에서 숫자 의미 해석 코드를 만들어야하며
    코드와 표시 문구의 연결이 필요하다
 

2. 장점
- SQL 조회 결과를 바로 이해할 수 있다.
- Select 결과 확인이 편하다


3. 단점
- 상태명이 변경되면 해당 상태명을 사용하는 SQL, C# 코드를 수정해야함


4. 자료형 결정 이유
- nvarchar(20)
 → 한글 상태명을 직접 저장할 수 있다.
 → 현재 상태명에는 충분한 길이이다.


5. 역할
① DB에서의 역할
- 주문 한 건의 현재 상태를 저장한다.
 → 주문 접수 시 상태는 '접수'로 저장
 → 주문 취소 시 기존 주문 행의 OrderStatus를 '취소'로 변경.
 → 취소하더라도 주문 행은 삭제하지 않음. 

② C#_Kiosk
- 주문 조회 시 상태를 표시 가능
- 주문 취소 요청 시 상태 변경을 연결
- C#_키오스크의 장바구니 취소 버튼과 DB의 주문 취소는 다른 기능
 → C#_키오스크의 장바구니 취소 버튼: 장바구니 비움
 → DB 주문 취소: 주문이 되었던 기록을 취소로 상태 변경
- 관련 C# 연동은 아직 미구현

③ 실제 주문 버튼을 누르면 DB 저장과 영수증 표시는 어떻게 연결되나?
- C#에서 주문 버튼을 누르면 현재 장바구니를 기준으로 저장을 시작
- 같은 트랜잭션에서 Orders에
 주문 행을 insert하고 생성된 OrderId를 받음
- OrderStatus는 생략해서 Default인 접수가 들어가게 함
- 받은 OrderId로 OrderDetail에 주문 상품들을 저장한다.
- 커밋이 성공하면 해당 OrderId로 영수증을 띄운다.
 → 기존 ReceiptData에 주문번호를 전달하는 방식으로 연결할 수 있다.
- 저장에 실패하면 영수증을 띄우지 않고 
 실패를 안내하며 장바구니를 유지한다.

- 예를 들면
→ OrderId = 3을 받은 뒤 
상세 저장에 실패해 롤백되면 주문은 저장되지 않음.
→ 하지만 자동 증가 번호는 이미 할당됐으므로
 다음 성공 주문이 4가 될 수 있다.
→ 따라서 번호가 비었는지와 주문 저장이 성공했는지는 별개이고,
  저장 성공은 커밋을 기준으로 판단할 것임 


6. 제약 조건 구상
① NOT NULL 
- 상태가 없는 주문 행을 방지한다.

② DEFAULT 
- 신규 저장 주문의 초기 상태를 '접수'로 정한다.
 → 상태값을 누락했을 때만 적용됨. 
 → 만약 Null을 명시하면 NOT NULL제약에 걸린다
 → 초기 상태는 '접수'로 하고, 취소SQL을 따로 생성한다.

③ CHECK 
- 값의 범위를 '접수', '취소'만 허용함


7. 주의점
- DB 취소는 기존 장바구니 초기화와 다름
- 취소된 주문 내역은 조회가 가능하다.
- Orders와 OrderDetail의 저장은 같은 트랜잭션에서 처리할 계획이다.

## <4. 총 수량(TotalCount) 열 설계>
1. 설계 대안
- 이후 OrderDetail 테이블을 만들어 상품별 수량을 저장해두고,
 주문 조회 발생 시 상세 수량을 합산하는 방식으로 한다. 


2. 장점
- 총수량이 필요할 때 주문 상세의 수량을 합산한다. 
- 상세 수량이 변경되어도
 Orders의 합계를 별도로 갱신할 필요가 없어,
 저장된 총수량과 상세 합계가 어긋날 가능성을 없어진다.


3. 단점
- 총 수량 조회 시 마다 상세 행 합산이 필요하다.
 → 미리 컬럼값으로 저장이 안되어있으니 연산이 필요해지는 것.


4. 자료형 결정 이유
- 해당 열이 없으므로 자료형을 확정하지 않는다.


5. 역할
① DB에서의 역할
- OrderDetail 수량에서 계산
 → 주문 한 건의 상품 수량 합계
 → 상품 종류 수와는 다른 값
    ex. 상품 A 2개, 상품 B 1개라면 
        총수량 3개, 상품 종류 2개

② C#_Kiosk
- DB 조회 결과의 합계를
 ReceiptData.TotalCount로 전달할 수 있다.
- 실제 저장 및 조회 연동은 미구현.


6. 제약 조건 구상
- Orders에 TotalCount 열을 두지 않으므로 해당 열의 제약조건은 없다.


7. 주의점
- UI에서 표시하는 총수량과 DB에서 조회하는 총수량은 일치해야 함.
- OrderDetail 저장이 실패하면 주문 전체를 롤백하는 방향이 기록됨.
- OrderDetail에는 상품별 수량이 필요함.
- 상세 테이블의 열과 제약조건은 아직 별도 설계 대상이다.

## <5. 총 합계 (TotalPrice) 열 설계>
1. 설계 대안
- 총 수량과 마찬가지로 OrderDetail에서 합산한다.
- Orders에 TotalPrice 열을 두지 않는다.
 → 주문 당시 상품별 가격과 수량을 OrderDetail에 저장하는 방향이다.

2. 장점
- Orders에 총금액을 중복 저장하지 않는다.
- 상세 금액과 별도 총 금액 사이의 불일치를 예방
 → 조회 시 합산하는 방식이니까
- 현재 정규화 방향과 일치


3. 단점
- 총금액 조회마다 상세 각 메뉴의 수량에 따른 금액의 전체 합산이 필요
- 각 메뉴의 상세 금액이 잘못 기재 되었을 경우 올바른 총금액 계산어려움


4. 자료형 결정 이유
- Orders에는 TotalPrice 열이 없으므로 
 해당 열의 자료형을 결정하지 않는다.


5. 역할
① DB에서의 역할
- 한 주문에 포함된 상품 금액의 합계.
- OrderDetail의 주문 당시 가격과 상품별 수량을 기준으로 계산한다.
 → 합산 식: 메뉴 단가 x 수량
 → ex. 상품 A: 당시 단가 1,000원, 수량 2개: 1,000×2 = 2000

② C#_Kiosk
- ReceiptData.TotalPrice는 유지한다.
- 주문 조회 시 DB에서 계산한 총금액을
 ReceiptData.TotalPrice에 전달할 수 있다.


6. 제약 조건 구상
- Orders에 TotalPrice 열을 만들지 않으므로 제약조건은없다


7. 주의점
- OrderDetail의 가격은 주문 당시 값이다.
- 상품 가격이 나중에 변경되더라도 
 과거 주문금액이 바뀌지 않아야 한다.
- Orders행과 OrderDetail행은 같은 트랜잭션에 넣어서 관리하고
 커밋 성공 후 영수증을 표시한다.
