
# 주문 상세 (OrderDetail)
- 주문 한 건에 포함된 메뉴별 정보를 여러행으로 나누어 저장한다.
  → 상세 한 행에는 특정 메뉴의 수량과 주문 당시 단가를 저장한다
- Orders는 주문 한 건의 공통 정보
- OrderDetail은 각 주문 메뉴 정보


## <전체 테이블 초안>
열 이름	            자료형	          역할
OrderDetailId       int               주문 상세 행의 고유 식별값
OrderId             int               Orders의 주문 식별값 참조
MenuId              int               Menu의 상품 식별값 참조
Menuname            nvarchar(100)     주문 당시 메뉴명 보관
UnitPrice           decimal(10,2)     주문 당시 메뉴 단가
Quantity            int               주문한 해당 메뉴의 개수

[ex. 이후 총계, 총량 계산]
- Orders Table
OrderId = 12

- OrderDetail Table
행 1 → OrderId 12, 상품 A, 수량(Quantity) 2
행 2 → OrderId 12, 상품 B, 수량(Quantity) 1

TotalCount = 2 + 1 = 3
TotalPrice = (A단가×2) + (B단가×1)


## <실제 동작 흐름>
C# 주문 버튼 클릭
├─ 장바구니 메뉴 목록 확보
├─ 빈 장바구니인지 확인
├─ DB 트랜잭션 시작 (주문 행, 주문 상세 행)
├─ Orders 한 행 INSERT
├─ 생성된 OrderId, OrderTime 확보
├─  OrderDetail 상품별 행 INSERT
└─ 모든 상세 저장에 성공?
      ├─ 성공: Commit
       |      ├─ ReceiptData 구성
       |      └─ ReceiptForm 표시
       |
      └─ 실패: Rollback
              ├─ 실패 안내
              └─ 장바구니 유지


[주요 부분]
- 영수증은 Commit 성공 후 표시한다.
- 단가는 주문 당시를 기준으로 한다.
  → 조회 시 현재의 가격을 과거 주문 가격 대신 사용되지 않도록 주의

## <1. 주문 상세 식별값(OrderDetailId) 열 설계>
1. OrderDetailId 하나만 사용허여 설계
 → OrderId와 MenuId는 별도 열
 → 자동 번호를 부여

2. 장점
- 상세 한 행을 단일 값으로 식별 가능
- 상세 행 개별 참조 쉬움

3. 단점
- 행이 늘어난다.
- 단독 PK만으로 같은 주문의 같은 상품 중복 저장을 막지 못해 
  중복 메뉴 행 정책을 따로 정해야한다.


4. 자료형 결정 이유
- 현재의 규모에서는 int도 충분하며,
 Orders.OrderId와 같은 정수형이다.


5. 역할
① DB에서의 역할
- 각 주문 상세 행의 PK 

② C#_Kiosk
- 영수증 표시에는 불필요.
- 상세 수정·조회 기능에 활용 가능.


6. 제약 조건 구상
- PRIMARY KEY
- IDENTITY(1,1)


7. 주의점
- OrderId와 용도가 다르다.

[같은 메뉴의 중복 저장 방지]
- 한 주문에서 같은 상품이 두 행으로 저장되는 상황 방지
- 상품별 수량을 관리하는 구조이므로, 
 한 주문에서 동일한 MenuId는 한 행만 저장되도록 제약을 걺

CONSTRAINT UQ_OrderDetail_Order_Menu
    UNIQUE (OrderId, MenuId)
 → 상세 행마다 고유한 OrderDetailId를 유지 및 동일한 메뉴 중복 방지

## <2. 주문 참조값(OrderId) 설계>
1. Orders.OrderId를 그대로 참조한다.
- 주문 상세마다 OrderId를 보관한다.


2. 장점
- 어떤 주문에 속하는지 명확하다.
- 주문별 상세를 쉽게 조회한다.


3. 단점
- Orders 먼저 저장해야 한다.
- 부모가 없는 상세는 넣을 수 없다.


4. 자료형 결정 이유
Orders.OrderId와 같은 int 사용.


5. 역할
① DB에서의 역할
- Orders와 OrderDetail를 연결.

② C#_Kiosk
- Orders INSERT로 발급된 ID를 상세 INSERT에 전달한다.


6. 제약 조건 구상
- NOT NULL
- FOREIGN KEY → Orders(OrderId)


7. 주의점
- 삭제 시 동작은 별도로 구현
- 취소는 행 삭제가 아닌 상태 변경
 → 의문점. 이러러면 OrderDetail에도 OrderStatus가 있어야하지 않나?
 → OrderId로 Orders를 연결해서 읽으면 되니 불필요함

## <3. 상품 참조값(MenuId) 설계>
1. Menu.MenuId를 주문 상세에 보관.
- Menu의 상품을 식별하는 기준이다.

2. 장점
- 상품과 상세의 관계가 명확하다.
- 상품별 판매 내역을 조회할 수 있다.

3. 단점
- 상품 삭제 정책에 영향을 받는다.
- 과거 주문과 Menu 관계를 고려해야 한다.
 → 의문점. 주문 당시의 상품의 상태를 저장있는데 어떤 관계 고려?
 → MenuId에 외래키를 걸면 
   주문 상세가 참조하는 Menu행은 삭제할 수 없는 문제가 생김.


4. 자료형 결정 이유
- Menu.MenuId와 같은 int 사용

5. 역할
① DB에서의 역할
- 주문된 상품의 기준 식별값.

② C#_Kiosk
- 선택한 상품의 MenuId를 전달.
- 현재 모델에 식별값 보유 여부 확인.

6. 제약 조건 구상
- NOT NULL
- FOREIGN KEY → Menu(MenuId)


7. 주의점
- MenuId만으로 주문 당시 가격을 저장할 수 없음
- Menu 행 삭제에 대응에는 별도의 기능이 필요
 → FK 설정 때문에 주문상세가 참조 주인 MEnu 삭제 불가

## <4. 주문 당시 상품명(Menuname) 설계>
1. MenuName을 상세에 복사
- 주문 당시 상품명을 저장한다.

2. 장점
- 과거 영수증에 당시 이름이 남는다.
 → Menu명이 바뀌어도 과거 주문의 표시는 유지된다.

3. 단점
- 주문 시점의 이름 복사 기능이 필요
- 현재 MenuName과 중복 
 → 주문 당시에서 변경이 없다면 MenuName과 겹침.
 → 근데 이건 큰 단점이 아님. 변경에 대비하는 차원에서는 장점

4. 자료형 결정 이유
- nvarchar(100): Menu.MenuName과 길이를 맞춤.


5. 역할
① DB에서의 역할
- 과거 주문의 상품명 보존.

② C#_Kiosk
- 영수증 항목명 표시용으로 사용

6. 제약 조건 구상
- NOT NULL 
- 빈 문자열에 대응하는 기능은 별도로 구현


7. 주의점
- 이 값은 주문 당시 기록이다.
 → 현재 상품명 변경 시 갱신하지 않는다.

## <5. 주문 당시 단가(UnitPrice) 설계>
1. 주문 당시 UnitPrice 저장
- Menu 가격을 주문 시점에 복사

2. 장점
- 가격 변경 후에도 과거 금액 보존.
- 당시 금액으로 합계를 계산 가능

3. 단점
- 상세마다 가격을 저장해야 한다.


4. 자료형 결정 이유
- decimal(10,2) 
 → Menu.Price와 같은 자료형이다.
 → 금액을 정확한 십진수로 보관한다.


5. 역할
① DB에서의 역할
- 해당 상품의 주문 당시 단가.

② C#_Kiosk
- 상품별 금액 및 영수증 계산에 사용.


6. 제약 조건 구상
- NOT NULL
- CHECK (UnitPrice >= 0)


7. 주의점
- C#에서 전달하는 가격이 잘못됐다면 
 CHECK (UnitPrice >= 0)만으로는 발견할 수 없다
 → C#에서 100원만 전달해도 제약이 통과되니까
 → 따라서 실제 주문 저장 로직에서는 
   Menu의 현재 가격을 DB에서 확인하고,
   그 값을 주문 당시 가격으로 확정하는 방식을 택한다.

## <6. 메뉴별 수량(Quantity) 설계>
1. OrderDetail에 Quantity 열을 둔다.

2. 장점
- 메뉴 종류별 주문 개수가 명확하다.
- 전체 수량과 금액을 계산할 수 있다.

3. 단점
- C#_키오스크의 장바구니 수량과 일치하는지 여부 파악을 해야한다.
 → 예를 들어 장바구니에 2개를 담았는데 코드가 1개를 전달하면 
  Check(quantity >0) 제약을 통과할 수 있음.
 → 따라서 장바구니에 담긴 것이 
  코드로 정확히 전달되는지 확인 절차가 필요함

4. 자료형 결정 이유
- int 

5. 역할
① DB에서의 역할
- 해당 상세 상품의 주문 개수.

② C#_Kiosk
- 장바구니 선택 수량 전달.
- 조회 후 ReceiptItemData에 반영.


6. 제약 조건 구상
- NOT NULL
- CHECK (Quantity > 0)


7. 주의점
- 수량 0 또는 음수는 저장하지 않는다.

----- ----- ----- ----- ----- ----- ----- ----- ----- ----- ----- ----- ----- -----
## <7. 총수량 및 총금액 계산>
1. TotalCount
- Orders 및 OrderDetail에 별도 저장하지 않는다.
- 주문별 Quantity를 합산한다.

2. TotalPrice
- Orders 및 OrderDetail에 별도 저장하지 않는다.
- 상품별 UnitPrice×Quantity를 합산.

3. 장점
- 상세와 별도 합계의 불일치를 줄이는 설계다.

4. 단점
- 주문 조회 때 합산 연산이 필요.
- 상세에 잘못 저장된 값은 계산 결과에도 영향을 준다.

5. 주의점
- OrderId별로 집계해야 한다.
- 상세 행이 없는 주문을 방지할 트랜잭션 검증이 필요하다. (핵심)
 → 상세 저장에 실패해서 주문번호만 존재하고 
  구매 품목이 없는 주문이 생길 가능성이 있다.
 → 이때 외래키 제약은 
  상세가 참조하는 주문이 있는지만 확인하니 검증이 불확실하다.
 → 따라서 빈 장바구니는 저장 전에 차단하고,
  주문과 상세를 한 트랜잭션에 넣어 
  전부 저장되었을 때만 Commit하고, 실패하면 전부 Rollback한다.
 
- 합계 계산 SQL은 추후 작성한다.

## <8. 후속 구현 및 검증 후보>
1. OrderDetail 생성 및 제약 검증
- PK, FK, NOT NULL, CHECK 확인.
- 없는 OrderId 또는 MenuId 차단.
- 수량이 0, 음수인 경우 차단.
- 음수 단가 차단.

2. 주문 저장 트랜잭션
- Orders와 OrderDetail를 함께 저장한다.
- 일부 상세 실패 시 전체 롤백.
- COMMIT 전 영수증을 표시하지 않는다.

3. 조회 및 합계 검증
- 주문별 상세 목록 조회.
- TotalCount와 TotalPrice 일치 확인.
- 주문 당시 가격 유지 확인.
- 상품명 변경 후 표시 정책 확인.

4. C# 연동
- 현재 모델의 MenuId 보유 확인.
- 주문 요청 모델과 조회 모델 구분.
- DB 저장 결과를 ReceiptData로 전달.
- 저장 실패 시 장바구니 유지.
