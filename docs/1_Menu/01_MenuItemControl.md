# 1. 역할
- 메뉴 하나를 화면에 표시하는 UserControl을 만든다.
- 메뉴 하나의 UI만 담당한다.
- 다른 메뉴나 상위 화면의 동작은 직접 처리하지 않는다.


# 2. 설계 기준
1. 하나의 메뉴만 담당
- MenuItemControl은 메뉴 하나의 UI를 담당한다.

2. 내부 UI 변경은 직접 담당
- 외부에서는 속성을 통해 필요한 값을 전달한다.
- 내부에서는 전달받은 값을 반영한다.
  → 다른 UI가 내부 컨트롤을 직접 수정하지 못하게 한다.


3. 동작 전달은 Event 사용
- 메뉴 선택과 같은 동작은 Event를 통해 외부에 알린다
 → 왜? 메뉴가 사용자에게 선택을 받는다 해도 이 UI에는 영향이 없음
   따라서 이 동작으로 영향을 받는 UI에서 핸들러를 구현하며 동작 정의.


# 3. 구현 전 판단
## [구현 완료]
- 재사용 가능한 둥근 UI 외형
 → RoundedPanel 


## [구현 계획]
- 메뉴마다 UserControl을 하나씩 직접 만드는 것이 아닌 메뉴 데이터를 목록에 따로 저장해두고, 
  그 목록에서 하나씩 가져와서 상품 UI를 만드는 구조를 구상하고 있다.

- 먼저 공통의 메뉴 데이터 틀과, 메뉴 컨트롤의 틀이 필요하다
  → 모든 메뉴의 데이터 형태와 UI의 기본 구조는 동일할 것이니까
  → 결국 이 공통의 틀에서 각 메뉴마다 실제로 들어가는 상세 속성값만 달라지는 것이다

- 이 구상을 위해 필요한 것은?
1. 메뉴 하나의 데이터 
2. 여러 메뉴 데이터을 보관할 목록
3. 메뉴 목록으로 UI를 만드는 로직


## 세부 구상 실현 계획
[1. 메뉴 하나의 데이터]
- 모든 메뉴의 공통적인 형태를 정의해둔다.
→ 여러 메뉴를 상품 목록에 넣어둘 것이니 각 메뉴를 구별할 번호인  id속성도 형태 안에 넣어두자.
→ ID, 메뉴명, 가격, 이미지


[2. 여러 메뉴 데이터을 보관할 목록]
- 메뉴 데이터 목록이 MenuItemControl의 책임이 맞을까?
→ 가지고 있을 수도 있을 것 같다.
→ 그러나 메뉴 하나의 UI가 여러 메뉴 데이터의 목록을 지니는 것은 역할이 과하다고 생각된다.
→ 메뉴 데이터 목록을 지니는 것은 여러 메뉴를 관리하는 상위 영역의 역할이라고 생각된다.


[3. 메뉴 목록으로 UI를 만드는 로직]
- 메뉴을 생성해내는 것은 MenuItemControl의 책임이 맞을까?
→ 아니다. 
→ MenuItemControl은 메뉴 하나의 UI를 담당하기로 했는데
  메뉴 목록을 받아서 자기 자신을 여러개 만들어내는 구조는 자연스럽지 않다.

- 그러면?
→ 여러 메뉴를 보여주는 메뉴판에서 메뉴 목록을 담당한다
→ 목록을 하나씩 확인한다.
→ 각 메뉴 데이터마다 MenuItemControl 하나를 생성한다


[4. MenuItemControl가 상품 목록, UI 생성 로직을 담당할 수 있을까?]
- MenuItemControl 자체에서 메뉴 목록을 지니고,
  목록을 기준으로 new MenuItemControl()을 사용해 여러 메뉴 UI를 만든 뒤 상위로 ui를 통채로 주는 형식이면 될 거 같다.

- 
[5. 최종적으로 MenuItemControl의 책임은?]
1. 상품 목록에서 상품 데이터를 전달받아 넣을 공간의 정의가 필요하다. 
- 아이디, 상품명, 상품가격, 이미지에 대한 공간이다.

2. 사용자가 눌렀을 때 알려줄 이벤트가 필요하다.
- 사용자가 MenuItemControl을 누르면 실제로 영향을 받는 것은 상위 UI들이다  
- 따라서 MenuItemControl은 상위 UI를 직접 변경하는 것이 아닌 자신이 눌려졌다는 알림을 줘야한다.
→ 설계 기준에 따라 UI 간 동작 알림은 알림은 이벤트로 전달하기로 했으니 
   MenuItemControl의 선택 사실을 이벤트로 구현한다.  


# 4. 구현 방향
MenuItemControl
→ 메뉴 하나의 UI 담당
→ 메뉴 데이터 전달받아 내부 UI에 값 표시
→ 둥근 외형은 RoundedPanel 재사용
→ 사용자 선택 감지해 Event로 상위에 알림
